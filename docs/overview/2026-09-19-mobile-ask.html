01TL;DR

Resumen ejecutivo

Los pills Ask y Agents de Market dejan de ser «coming soon»: un agente (Claude Sonnet 5 con su persona) da una lectura pagada con créditos simulados sobre una celda de la matriz nivel × horizonte —probabilidad, tres razones, límites— y un cron la resuelve right/wrong contra el mark real de Perpl y avisa por push. Agents lista los agentes con récord verificable; Trade sigue manual y gana order book L2 y «Trade this level» con recordatorios. Backend propio en el esquema mobile del Supabase compartido con Gilbert.

Decisiones que lo ordenan: la matriz es 5 niveles × 4 horizontes sobre el mark real; el cobro es simulado (20 créditos por wallet, reembolso si la lectura no llega en 60 s); la identidad es una firma de wallet válida 24 h; el modelo es claude-sonnet-5 con salida estructurada; los pushes salen del servidor por APNs directo (con fallback local decidido de antemano). Sin cierre automático ni take-profit: fuera del bounty. Cuatro fases con checkpoint; al cierre, build 6 de TestFlight. Deadline: 13 oct 2026.

03Decisiones clave

Decisión Por qué
D1–D2 · Una read = pregunta binaria sobre una celda; matriz +2.5 · +1.0 · +0.5 · −0.5 · −1.0 % × 1H · 4H · 12H · 24H Probabilidad de «sí», tres razones y límites; el target sale del mark real de Perpl que el servidor vuelve a leer al crear la read. Verificable por un jurado: número, fecha, resultado.
D3 · Cron por minuto resuelve right/wrong y Brier contra pub/context; 30 min sin Perpl → void + reembolso Un minuto es el grano del horizonte más corto; void evita juzgar con un mark viejo.
D4–D5 · Backend propio en el Supabase pickler, esquema mobile, migrador propio vía Management API; seis edge functions con auth propia Proyecto compartido con Gilbert: nada de Drizzle, db push ni sus esquemas; el MCP de la sesión apunta a Proflores y no se usa.
D6 · Identidad = firma de wallet pickler-reads:<address>:<ts>, 24 h en SecureStore, headers en cada llamada Sin cuentas ni JWT: la wallet ya es la identidad. Un Face ID por día.
D7 · 20 créditos simulados por wallet; cobro e insert en una transacción; reembolso si el modelo falla o la read queda pending > 60 s Ledger auditable; la regla de 60 s se cumple por dos caminos independientes.
D8 · claude-sonnet-5 con messages.parse + output_config.format (zod); persona del agente cacheada; effort medium, timeout 50 s Salida estructurada sin parseo frágil; latencia bajo el minuto. El agente ve los mismos datos que el usuario.
D9 · Tres agentes seed (jesus primero, drift, anchor); récord desde la vista agent_records «El agente de Jesús» es la demo; dos personas más hacen que elegir agente signifique algo.
D10 · Push por APNs directo desde las funciones (key .p8, HTTP/2); permiso al confirmar la primera lectura; fallback local si el edge runtime no negocia HTTP/2 Sin cuenta de Expo ni EAS. El servidor sabe el resultado y el mark, por eso manda él. El fallback está decidido antes de probar.
D11 · Order book L2 por market-data WS, un socket por ticket visible, sin pings; parser puro con fixture Doc pública verificada 2026-09-19; límites de 16 subs y 10 req/min respetados por construcción.
D12 · «Trade this level» pone lado y LevelCard; recordatorios sólo tras filled/open; nada cierra la posición Puente lectura → trade real sin custodiar keys ni prometer un cierre que Perpl no ejecuta por tiempo.
D13–D16 · Store con askView, askCell, askAgentId, tradeLevel; pantallas ask.tsx, agents.tsx; módulos reads/* puros + useReads Misma arquitectura que Perpl: módulos puros con tests, un hook que orquesta.
D17–D18 · Cuatro fases con checkpoint; fuera: auto-cierre, take-profit, créditos reales, follow, Polymarket, Android 24 días; F1+F2 son el mínimo demostrable, F3 puede recortarse en el checkpoint de F2.
D19–D20 · Secretos vía supabase secrets set, cron secret en Vault, rate limit 10 reads/10 min por dirección, funciones idempotentes El servicio es público aunque la app sea privada; el API key de Anthropic sí vale.

04Modelo / arquitectura

Quién habla con quién y la tabla central del esquema mobile. El detalle completo (siete tablas, la vista agent_records, los contratos JSON de las seis funciones) está en el spec §2.

La app sólo habla con las funciones (firmadas) y con Perpl (market-data); el cron resuelve y APNs avisa.

Tabla central (SQL)

-- mobile.reads · una lectura por celda, agente y wallet (spec §2.1)
create table mobile.reads (
  id uuid primary key default gen_random_uuid(),
  address text not null references mobile.wallets(address),
  agent_id text not null references mobile.agents(id),
  market_id int not null, symbol text not null,
  level_bps int not null check (level_bps in (250, 100, 50, -50, -100)),
  horizon_min int not null check (horizon_min in (60, 240, 720, 1440)),
  price_decimals int not null, mark_at_request bigint not null, target bigint not null,
  question text not null,
  status text not null default 'pending'
    check (status in ('pending', 'open', 'right', 'wrong', 'void', 'failed')),
  probability numeric(4,3), reasons jsonb, limits text,
  model text, latency_ms int, usage jsonb, credits_charged int not null, error text,
  created_at timestamptz not null default now(), expires_at timestamptz not null,
  resolved_at timestamptz, mark_at_resolution bigint, outcome boolean, brier numeric(5,4)
);
create index on mobile.reads (expires_at) where status = 'open';
