1. Decisiones que fija este spec

#DecisiónValorPor qué
D1Qué es una lecturaUna read es la respuesta de un agente a la pregunta que arma una celda: ¿El mark de {symbol} estará en o por encima de {target} a las {expires_at}? (nivel positivo) o …en o por debajo de… (nivel negativo). La respuesta es probability (0.01–0.99, probabilidad de sí), reasons (exactamente 3, ≤ 140 caracteres cada una) y limits (≤ 240 caracteres: qué la invalidaría). El call del agente es yes si probability ≥ 0.5, no si no.Es lo que el prototipo prometía en Ask y lo que un jurado puede verificar: pregunta binaria, número, fecha, resultado.
D2La matrizLEVELS_BPS = [250, 100, 50, -50, -100] (filas, de arriba abajo) × HORIZONS_MIN = [60, 240, 720, 1440] (columnas 1H · 4H · 12H · 24H). target = round(mark × (1 + bps / 10000)) en unidades de priceDecimals; expires_at = created_at + horizon. El mark real es market.mark del GET /v1/pub/context de Perpl: la app lo usa para la vista previa de la celda y el servidor lo vuelve a leer al crear la lectura y guarda el suyo (mark_at_request); la app muestra los valores del servidor una vez creada.Escalera del prototipo (asimétrica a propósito: la app es para apostar a favor con apalancamiento). El servidor como fuente del mark evita lecturas armadas con un precio viejo o manipulado.
D3Resoluciónresolve-reads corre cada minuto (pg_cron → pg_net → la función, con x-cron-secret). Toma las reads open con expires_at ≤ now(), lee un pub/context, guarda mark_at_resolution y decide outcome (yes si mark ≥ target con nivel positivo, mark ≤ target con negativo; no si no). status = right si call = outcome, wrong si no; brier = (probability − outcome)² con outcome ∈ {0, 1}. Si Perpl no responde, la read se queda open y se reintenta al minuto; con más de 30 min de retraso pasa a void y reembolsa. Cada read resuelta o anulada genera un push (D10).Un cron por minuto es el grano del horizonte más corto (1H) sin desperdiciar llamadas; void evita marcar right/wrong con un mark viejo.
D4BackendSupabase proyecto pickler de Sherry Labs (yvdipvcrpbqvofayteqf), compartido con Relayerfi/pickler de Gilbert. Todo lo nuestro en el esquema mobile: tablas agents, wallets, credit_events, reads, reminders, devices, migrations y la vista agent_records (§2.1). Código en services/reads/ (§2.2). Prohibido: correr su migrador Drizzle, tocar public o cualquier esquema suyo, supabase db push / db reset (comparten supabase_migrations.schema_migrations con su historial), y el MCP de Supabase de la sesión (apunta a Proflores). Migraciones nuestras: SQL numerado en services/reads/supabase/migrations/, aplicado por services/reads/scripts/migrate.mjs contra el endpoint de consulta del Management API (POST /v1/projects/{ref}/database/query, token SUPABASE_ACCESS_TOKEN) con ledger propio mobile.migrations. Extensiones pg_cron y pg_net se habilitan sólo si no están (idempotente, no tocan esquemas ajenos). (F1) Las funciones acceden a mobile por SUPABASE_DB_URL con postgres.js (P1 del plan F1), no por PostgREST: mobile no se expone en la API del proyecto. Las migraciones aplicadas son cinco: 0001_schema, 0002_function_privileges (revoke execute a PUBLIC en las tres funciones security definer + guard de refund_read), 0003_seed_agents, 0004_cron, 0005_refund_transitions (revisión final F1: refund_read exige la transición correcta por estado, no cualquiera de pending/open).Un esquema propio aísla tablas, nombres y permisos; un migrador propio evita pisar el historial de Gilbert. El Management API es la vía que la CLI y el MCP usan por debajo, sin necesitar la contraseña de la base.
D5Edge functionsSeis, en services/reads/supabase/functions/<name>/index.ts con verify_jwt = false (auth propia, D6): agents-list (GET, público: agentes activos con récord); read-request (POST firmado: crea la read, cobra, llama al modelo, devuelve la read); read-get (GET firmado: una read por id, sólo del firmante); reads-list (GET firmado: reads del firmante, filtro opcional market_id, + créditos); reminder-set (POST firmado: crea los recordatorios de un nivel); resolve-reads (POST con x-cron-secret: resuelve reads vencidas, manda recordatorios vencidos, reembolsa pending huérfanas). Código compartido en _shared/ (auth.ts, db.ts, perpl.ts, claude.ts, apns.ts, matrix.ts). Con --no-verify-jwt al desplegar. (F1) resolve-reads acepta además { apnsSmoke: { token, env } } con el secreto del cron para probar APNs sin tocar la base; si faltan los secretos APNS_* responde 503 apns_unavailable (la rama normal sigue en 200).Una función por verbo del brainstorm más agents-list, que faltaba (exponer mobile por PostgREST tocaría la configuración de API del proyecto compartido).
D6Identidad y sesiónLa app firma con la cuenta de la wallet (wallet.account.signMessage, personal_sign) el texto pickler-reads:<address en minúsculas>:<timestamp ms> y manda en cada llamada firmada los headers x-pickler-address, x-pickler-ts, x-pickler-sig. El servidor verifica con verifyMessage de viem, acepta ts ∈ [now − 24 h, now + 5 min] y usa la dirección recuperada como identidad. La app guarda { address, ts, sig } en SecureStore (pickler.reads.v1, sin gate biométrico: la firma sólo autoriza créditos simulados y lecturas) y la renueva cuando faltan < 1 h; se firma con openWallet() (Face ID) la primera vez que Ask lo necesita y se borra en Sign out junto con la key de trading. (F2) La sesión se parte en src/reads/session.ts (puro: mensaje canónico, vigencia, headers, serialización) + src/storage/reads.ts (SecureStore, P1); se renueva con menos de 1 h de vida (P2); un 401 la descarta (dropSession) y Ask vuelve al gate — nunca se re-firma sola tras un 401: un flag droppedRef en useReads bloquea la firma silenciosa hasta que el usuario toque «Unlock» o pida otra lectura (revisión de Task 7; evita un bucle firma → 401 → firma cada 15 s). Con la wallet unlocked se firma sin prompt al activar Ask; locked muestra SessionGate y pide Face ID al tocar «Unlock» (P3).Sin cuentas ni JWT: la wallet ya es la identidad del producto. Stateless en el servidor. 24 h reduce prompts de Face ID a uno por día.
D7Créditosmobile.wallets(address pk, credits int); la primera llamada firmada de una dirección hace upsert con 20 créditos y evento grant. Cada agente tiene price_credits (seed: 1). read-request cobra en una sola transacción con el insert de la read (mobile.request_read(...), función SQL security definer); sin saldo → 402 { error: "no_credits" }. Reembolso (evento refund, read failed o void): si el modelo falla o tarda > 50 s dentro de read-request, o si el cron encuentra una read pending con más de 60 s (la función murió). Ledger `mobile.credit_events(delta, reason ∈ grantchargerefund, read_id)`. Sin compra de créditos.Cobro simulado y auditable: el saldo siempre es la suma del ledger. La regla de 60 s del brainstorm se cumple por dos caminos independientes.
D8El modeloclaude-sonnet-5 (fijado por Jesús) vía @anthropic-ai/sdk (npm: en Deno) con client.messages.parse y output_config.format = zodOutputFormat(ReadSchema) (probability number 0.01–0.99, reasons array de 3 strings ≤ 140, limits string ≤ 240). system = reglas fijas de Pickler + agents.persona (con cache_control: { type: "ephemeral" }); user = JSON con symbol, name, mark, prev, change24hPct, target, levelBps, horizonMin, expiresAtUtc, nowUtc. max_tokens: 1024, output_config.effort: "medium", timeout: 50_000 ms, maxRetries: 1. Se guardan model, latency_ms y usage (input_tokens, output_tokens) en la read. Sin herramientas ni búsqueda web en el bounty.Salida estructurada quita el parseo frágil; effort medium mantiene la lectura por debajo de los 60 s. Los datos que ve el agente son los mismos que ve el usuario (mark, 24 h): la lectura es honesta sobre su fuente.
D9Agentesmobile.agents(id, handle, name, owner, persona, price_credits, active, sort). Seed de tres: jesus ("Jesús's agent", owner = "Jesús", primero en sort; persona placeholder en el plan F1 que Jesús puede reescribir), drift (momentum: sigue el cambio 24 h) y anchor (reversión a la media). Récord por agente en la vista mobile.agent_records: reads, resolved, right, accuracy = right / resolved, brier_avg. El pill Agents lista agents-list con name, by {owner}, récord y precio; tocar uno lo preselecciona en Ask."El agente de Jesús" es la demo; dos personas más hacen que elegir agente signifique algo y que los récords diverjan. El récord sale de reads reales, no de un contador.
D10Notificaciones pushAPNs directo desde las funciones (_shared/apns.ts: JWT ES256 con WebCrypto a partir de APNS_KEY_P8_B64 ((F1) el .p8 completo en base64 de una línea, P7 del plan; antes decía APNS_KEY_P8), APNS_KEY_ID, APNS_TEAM_ID = 2PBQJ37Q8W; fetch HTTP/2 a api.push.apple.com para TestFlight y api.sandbox.push.apple.com para builds __DEV__). Tabla `mobile.devices(address, token, env ∈ sandboxproduction, updated_at); la app manda pushToken/pushEnv en read-request y reminder-set y el servidor hace upsert. App: expo-notifications (plugin → entitlement aps-environment), permiso pedido la **primera vez** que se confirma una lectura o un nivel; getDevicePushTokenAsync(); si el usuario niega, la app lo dice en la card y sigue sin push. Tres tipos: **resolución** ("BTC +1.0% · 4H — Jesús's agent was right"), **recordatorio previo** (15 min antes: "BTC at 65,120 · your level 65,900 · 15 min left") y **recordatorio al vencer** (con el mark). Tocar el push abre la app en market con el pill correspondiente. **Fallback registrado** (riesgo §4): si el fetch HTTP/2 a APNs no funciona desde el edge runtime en la prueba de F1, las tres notificaciones pasan a **locales** programadas por la app (sin mark en el texto) y mobile.devices queda sin uso. **(F2)** PUSH_MODE: "apns" \"local" en src/config/reads.ts (= "apns") conmuta APNs / local (P5); el permiso se pide dentro de ask() en la primera confirmación (P6) y el token viaja como pushToken/pushEnv (sandbox con DEV); el tap lee pickler de content.data (o data a secas) o del userInfo del trigger y navega con requireAccount("market", …) (P7). **Estado del smoke real: sin correr** (sin secretos APNS_; pushSent 0 en el cron); el tap se probó con xcrun simctl push` en caliente y en frío; el tap en frío exigió encolar el target hasta cargar la cuenta* (App.tsx, commit 3a15792: getLastNotificationResponseAsync resolvía con account === null y el gate mandaba a Sign in). El servidor es quien sabe el resultado y el mark; por eso manda él.
