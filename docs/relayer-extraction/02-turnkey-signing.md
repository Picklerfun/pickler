# Relayer extraction 02: Turnkey, wallets, policies, approvals and signing

- **Source:** Relayer `develop` at commit `bb6bb1226e9289f675e355e7c022530e1e790fd9`, `apps/api`, read-only snapshot.
- **Scope:** `src/kits/signing/{turnkey,wallets,approvals,transactions,recovery}`, `src/kits/signing/*.ts`, `src/blockchain`, `src/kits/agent/{cosigner,evm}`, and the Turnkey/signing parts of `src/kits/agent/agent-signing.service.ts`.
- **Target:** Pickler on Cloudflare Workers (Hono or fetch handlers, zod, supabase-js over fetch, WebCrypto or `node:crypto` with `nodejs_compat`, Durable Objects/KV/Queues/Cron Triggers), with Monad (EVM) as the chain and AUSD as the base stablecoin.

- **Paths:** paths are relative to `apps/api/src` unless they are marked otherwise. No secret values were read or reproduced.

## 0. Executive summary

1. **Custody model.** At this commit Relayer is fully self-custodial ("Phase 33 Branch A"). Each integrator gets its own Turnkey sub-organization. The only root user is the owner's passkey, with root quorum 1. Relayer's parent API key can **read** sub-orgs but cannot run mutating activities in them. The code comments call this `ORGANIZATION_MISMATCH` after the `relayerAdmin` removal. Every write is built on the server as an _unsigned activity_, stamped with the user's passkey in the browser, and forwarded unchanged by `TurnkeyActivityForwarderService`.
2. **Server-held keys.** Relayer holds only two kinds of key:
   - The **Relayer co-signer** P-256 API key for each sub-org, stored encrypted in `signing.turnkey_orgs.relayer_cosigner_encrypted_key`.
   - **Legacy delegated agent keys**, stored encrypted in `agent.agents.encrypted_turnkey_key`. These are NULL for V1 non-custodial agents.

   Both use `encryptAES256GCM`/`decryptAES256GCM` from `api/utils/crypto.util.ts`, keyed by the `ENCRYPTION_KEY` env var.

3. **Source of truth for policies.** Turnkey holds the truth. `signing.policies` is a best-effort cache, and it drifts in several places (§2.4).
4. **Dead or broken server-key paths** that should not be copied as-is:
   - The parent-key `TurnkeyPolicyService.create*`, `TurnkeySciService.ensureSci` and `SpendingSecurityService.save*` (the non-prepare variants).
   - `ApprovalService.approveRequest`'s parent-key `approveActivity`.
   - `AgentSigningService` (Solana-only delegated custody).
5. **EVM/Monad path to port first:** passkey-stamped wallet creation and accounts, then transaction prepare/confirm/broadcast with viem, then policy synthesis (`synthesize-policy.ts`) plus the prepare/confirm spending-security flow, then approvals. The EVM co-signer pieces (`EnforcementGate`, `CoSignerService`, `EvmIntentInspector`, `EvmTxBuilder`) are small and portable but hard-coded to Base USDC.
6. **Main Workers blockers:**
   - `cache-manager`/Redis saga state, including a cached _encrypted private key_.
   - `@nestjs/schedule` crons.
   - `node:crypto` APIs that Workers does not implement or handles poorly: `createECDH`, `generateKeyPairSync`, Ed25519 `KeyObject` verify, and `scryptSync` CPU cost.
   - `@turnkey/sdk-server` runtime assumptions.
   - The WebSocket gateway.
   - Multi-second `setTimeout` polling.
   - A hard-coded RPC provider key in `blockchain/config/rpc.config.ts`.

### 2.4 How Supabase policy rows sync with effective Turnkey policies

**Effective policy = the Turnkey sub-org's policy set** (plus root-quorum semantics). `signing.policies` is a cache with several independent writers.

1. **Spending & Security**, the active path (`wallets/services/spending-security.service.ts`, routes in `wallets/spending-security.controller.ts`).
   - **Read:** `listSpendingPolicies` lists **Turnkey** policies through the parent read key (`TurnkeyPolicyService.getPolicies`) and parses the `notes` grammar:
     - `spending-maximum:<USDC|USDT>:<chain>:amt=<int>` → DENY `eth.tx.to == token && contract_call_args['amount'] > raw`
     - `spending-exception:<TOKEN>:<chain>:amt=<int>:sigs=<n>` → ALLOW `< raw`, admin-tag consensus
     - `spending-block-swaps` → DENY on UniswapV2 selectors
     - `spending-app-review` → DENY on `0x095ea7b3`

     Only chains in `SUPPORTED_CHAINS_FOR_LAYER` (`ethereum, base, arbitrum, optimism, polygon, avalanche`) are recognised. **The DB is not read.**

   - **Prepare:** diffs desired against Turnkey and emits unsigned `CREATE_SMART_CONTRACT_INTERFACE` (if `findSci` misses), `CREATE_POLICY_V3`, `UPDATE_POLICY_V2` (policy id preserved) and `DELETE_POLICY_V1`. It caches `SaveMaximumOpState` / `SaveExceptionOpState` / `SaveToggleOpState` under `signing-op-request:sor-<uuid>` for 10 minutes with a 16-byte nonce.
   - **Confirm:** one-shot cache delete, then for each row: activity-type match check, forward, then
     - `COMPLETED` → DB write (`insertOne` with `policy_type='turnkey_native'`, `network='mainnet'`, `config_json.synth='spending_security'`, and `activity`/`effect`/`rule`/`scope_json`/`threshold`)
     - `CONSENSUS_NEEDED` → reported as `queued` with **no DB write, ever**
     - `REJECTED`/`FAILED` → reported
   - **Drift bugs:**
     - Update and delete entries carry `existingDbId: ''`, so `persist*Outcome` updates or soft-deletes `id = ''`, a no-op. Stale `active` rows remain after passkey updates and deletes.
     - Queued (multi-admin) creates never land in the DB.
     - Since the pre-check and wallet enrichment read the DB, they can disagree with Turnkey.
   - The non-passkey methods `saveMaxima`, `saveExceptions` and `saveBlanketToggle` diff against **DB** rows and call parent-key create/delete with rollback. No controller uses them, and they would hit `ORGANIZATION_MISMATCH`. **Exclude.**
2. **Agent policies** (`kits/agent/agent.service.ts`, confirm-create-agent-policies ~L2790). `ACTIVITY_TYPE_CREATE_POLICIES` is stamped by passkey. Rows are inserted with `agent_id`, `turnkey_policy_id` matched **by array index** to `createPoliciesResult.policyIds`, `network='testnet'`, `effect` mapped from `EFFECT_DENY`, and `scope_json` from `buildAgentPolicies`. Insert failure is logged, not thrown ("resync on list"; no resync exists). `agent.agent_policy_meta` mirrors `max_per_tx` and `allowlist` for the co-sign `RuleSource`.
3. **Signoff rules** (`core/auth/signoff/signoff-rules.service.ts`, out of scope): a separate `signoff_rules` table with `turnkey_policy_id` (migration 0069).
4. **Legacy `policy_type` rows** (`spending_cap`, `per_tx_limit`, `destination_allowlist`, `chain_restriction`, `token_allowlist` with `config_json.*_raw`). Only `PolicyPreCheckService` and `WalletsService.loadMasterPolicy` read them. The removed `PolicyManagementService` wrote them; no current writer exists apart from the mislabelled agent rows (B2).
5. **Off-chain clauses** (`scope_json.clauses[].layer='offchain'`, `usd_value` / `beneficiary`): evaluated fail-closed by `offchain-clause-evaluator.ts` + `TokenPriceService` (stablecoins = $1, everything else throws `PriceUnknownError`). No writer exists in the API; the web presumably writes them.
6. **Reconciliation:** none. There is no cron, no webhook-driven resync and no `status='rotating'|'pending_delete'` handling.

**Pickler recommendation:**

- Treat Turnkey as authoritative.
- Keep `signing.policies` as a projection keyed by `turnkey_policy_id` (not by DB `id`).
- Upsert on `COMPLETED` **and** when a queued activity later completes, via a reconciler: Cron Trigger or Turnkey `ACTIVITY_UPDATES` webhook → `getActivity` → persist.
- Add a periodic full resync from `getPolicies` using the `notes` grammar.

## 3. File-by-file classification

Legend:

- **COPY:** copy verbatim; at most import-path or `Logger` swaps.
- **ADAPT:** keep the logic but change the runtime surface.
- **EXCLUDE:** do not port, with the reason given.

"Deps" lists internal (Relayer) imports only.

Common adaptations apply to every ADAPT row and are not repeated:

- Remove `@Injectable`/`@Inject`/modules and wire through a composition root (Pickler: `apps/web/src/server` or a Worker entry).
- `Logger` → a structured `console` logger.
- `HttpException`/`BadRequestException`/... → a domain error type mapped to HTTP in Hono.
- `process.env` → Worker `env` bindings passed in.
- `class-validator` DTOs → zod schemas in `packages/api-schema`.
- `@kits/...` path aliases → workspace package imports.

Proposed Pickler placement (respecting `AGENTS.md` layering): pure rules go in `packages/core`, SDK/DB/RPC adapters in `packages/infrastructure`, HTTP in the Worker/web server layer, and chain constants in `packages/chain`.

## 4. Dependency-ordered porting sequence (EVM/Monad first)

Each step depends only on earlier steps. Items marked (T) include porting the matching specs.

**Step 0: spikes that de-risk everything (do these first)**

1. **Turnkey client on workerd:** a Worker that (a) signs a query (`get_whoami` or `get_organization`) with an API key and (b) forwards a stamped activity. Compare three options: `@turnkey/sdk-server` with `nodejs_compat`; `@turnkey/http` `TurnkeyClient` + `@turnkey/api-key-stamper`; and a hand-written WebCrypto stamper (§5).
